# 决策：镜像基线退回 CE 13.0

一份架构决策记录（ADR）。配套：[BRANCHES.md](BRANCHES.md)（原则 0）、
[AGENTS.md](../AGENTS.md)（构建前提）、[storage.md](storage.md)。

## 决策

**CloudFile 的镜像基线从"14.0 从源码构建"退回到"基于官方已发布的 CE 13.0"。**
当上游发布 CE 14.0 镜像/tag 时再前移——那时改成 `FROM` 官方镜像，彻底不再需要
"从源码重构一个 CE 版本"这条路。

## 背景与理由（均已核对代码）

原选择是 14.0，但**"为什么 14.0 而非 13.0"从未记录**——现有文档只讲了 14.0
怎么从源码构建，没讲为什么不用 13.0。据此重新权衡：

| 事实 | 核对结果 |
|---|---|
| CE 14.0 是否发布 | ❌ 上游只有 `-pro` tag，**没有 CE 14.0 发布/镜像**。14.0 CE 是从 master SHA 拼出来的 |
| CE 13.0 是否发布 | ✅ 官方已发布、有 `seafileltd/seafile-mc:13.0` 镜像、有 tag |
| 13.0 是否已含 roadmap 依赖的栈 | ✅ `repo_metadata`、`tags`、`file_tags`、`repo_tags`、`frontend/src/metadata`、seasearch **全在 13.0** |
| Django 版本 | 两版都是 **5.2**，无版本悬崖 |
| 5 个上游补丁目标 + `check_folder_permission` + 身份映射 | ✅ **13.0 全部存在**，扩展点无需重新设计 |
| 14.0 相对 13.0 | 领先 1269 commit，但**无新增子系统**，是同结构内的增量修订 |
| 13.0 分支是否干净 | ✅ `origin/seahub-13`、`origin/seafile-13` 均为干净上游，是可直接叠加的基座 |
| 13.0 镜像配方 | ✅ **仓库里已有** `image/seafile_13.0/Dockerfile`（上游 CE 13.0 官方配方），是现成起点 |

**决定性的一条是时间性的**：14.0 从源码构建这条路，**只因为上游还没发布 CE 14.0
镜像而存在**。而 13.0 今天就有官方镜像、有 tag、有发布。所以退回 13.0 = 拿"已发布、
已测试、有官方镜像可校验"的代码作基线，而不是拿 master SHA 拼一个上游从未以 CE
形式发布过的版本。这也正是刚确立的[原则 0（优先复用官方组件）](BRANCHES.md#〇首要原则优先复用官方组件)
的直接推论。

## 一条必须诚实的边界：13.0 不等于"零构建"

**CloudFile 修改了 C/Go 服务端**（`cf-ext.c` 的 ACL 强制、目录列举过滤，以及将来
的 S3 驱动），所以 **seaf-server / fileserver 的二进制无论基线是 13 还是 14 都得从
fork 编译**——不能直接用官方镜像里预编译的那份。

因此 13.0 的收益**不是**"改个 `FROM` 就不用编译了"，而是：

1. **对着已发布、已测试、打了 tag 的 13.0 代码编译**，而不是对着 14.0 的 master SHA。
2. **依赖/pin 是官方 13.0 的已知良好组合**——十二次构建失败里那一类（Node 版本、
   系统库、依赖链、版本号格式）大多来自"从零拼 14.0 环境"，改用官方 13.0 配方后
   直接消失。
3. **有官方 `seafile-mc:13.0` 镜像可 diff 校验**：你构建出的东西能和官方比对，
   证明只差 CloudFile 的改动。

> `seafile-mc` 镜像本身也是 `FROM ubuntu:24.04` + 复制发布包——不是什么特殊基座。
> 所以"基于官方镜像"在镜像层面主要是**复用它的配方与依赖**，而不是把它当作不可
> 拆解的黑盒 FROM（那会和"覆盖自编译的服务端二进制"打架）。

## 优缺点

**退回 13.0（本决策）**
- ➕ 符合原则 0；对着已发布/已测试/有 tag 的代码构建。
- ➕ 消除"从零拼 14.0 环境"那一类构建失败；有官方镜像可校验。
- ➕ roadmap 一样都不少（13.0 已含全部栈）。
- ➕ 官方当前稳定版，CE 用户实际在跑的平台。
- ➖ 需按 13.0 行号重验两个已落地能力（dir-acl、SSO）。有界——目标文件全在、
  架构版本无关——但是真实工作。
- ➖ 跟随 13.x 维护线，少了 1269 commit 的修订。缓解：13.0 是当前稳定版、非 EOL；
  点发布会回合安全补丁。

**维持 14.0 从源码**
- ➕ 代码最新；跟随上游活跃线。
- ➕ 已构建通过，十二次失败已付清并沉淀进 preflight/verify-local。
- ➖ 永久自担一个"CE 版本从源码重构"的构建——is_pro 门控与 Pro 镜像许可张力的来源。
- ➖ 与原则 0 相悖。

## 迁移计划（分阶段，尚未执行）

前提：确认无 14.0 特定驱动（客户要 14.0-only 能力 / 13.0 有 EOL 日期）。roadmap 内
未发现。

| 阶段 | 内容 |
|---|---|
| **1 重接 fork** | hub：从 `origin/seahub-13` 起新基线，`cloudfile_ext/`（新文件）直接叠加；5 个上游补丁按 13.0 行号逐一重贴并核对锚点。server：从 `origin/seafile-13` 起，重加 `cf-ext.c/h` + `cloudfile.sql` + 8 个补丁。**清单目标仍是 5/8/3 逐字节可核** |
| **2 镜像与清单** | `release.yaml` 各组件 pin 到 13.0 SHA（seahub-13/seafile-13 及 seafevents/seafobj/seafdav/libsearpc/libevhtp 的 13.0 兼容 SHA）；Dockerfile 以**已在仓库的** `image/seafile_13.0/Dockerfile` 为起点 + CloudFile 叠加；`build/image/scripts` 的 `_14.0` 命名改 `_13.0` |
| **3 验证** | 基线门禁（smoke + baseline）跑 13.0；重跑 dir-acl 六入口矩阵 + SSO 两阶段矩阵；`check-upstream-patches.sh` 复核清单 |
| **4 收尾** | 更新 [AGENTS.md](../AGENTS.md) 的"14.0 CE 不存在"前提（改为"以已发布 13.0 为基线"）；`preflight-checks.py` 与各 doc 的版本串；本决策标记为已执行 |

## 退出路径

**当上游发布 CE 14.0 镜像/tag** —— 那时把基线前移到 14.0（甚至直接 `FROM` 官方
CE 14.0 镜像叠加），从源码重构 CE 这条路就此退休。届时的迁移与本次同构、更省：
目标从"master SHA"变成"官方发布"。
