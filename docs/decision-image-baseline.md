# 决策：镜像基线维持 CE 14.0

架构决策记录（ADR）。配套：[BRANCHES.md](BRANCHES.md)（原则 0）、[AGENTS.md](../AGENTS.md)。

## 决策

**镜像基线保持"14.0 从 CE 源码构建"。** 当上游发布 CE 14.0 镜像/tag 时，改为基于
该官方镜像——因为已在 14.0，这是**同版本平移**，不是版本迁移。

## 背景

上游没有 CE 14.0 发布（只有 `-pro` tag、只有 CE 13.0 镜像），所以 14.0 只能从 CE
源码构建。曾据此考虑退回已发布、有官方镜像的 **CE 13.0**。

## 为什么不退回 13.0

**CloudFile 改了 C/Go 服务端**（`cf-ext.c` 的 ACL 强制、列举过滤，及将来的 S3 驱动），
所以 `seaf-server`/`fileserver` **无论 13 还是 14 都得从 fork 编译**——官方镜像里
预编译的那份用不了，`seafile-mc` 本身也只是 `FROM ubuntu` + 发布包。

一旦重新编译两版都免不了，13.0"复用官方镜像、免于从源码构建"的核心收益就不成立，
决策退化为"更旧但已发布(13) vs 当前且已跑通(14)"。14 胜出：14.0 构建已跑通
（12/12 冒烟，沉没成本已付），维持它迁移成本为零；而退回 13.0 要重贴 13 个补丁、
重验两个能力、落后 1269 commit，且**将来上游发 CE 14.0 时还要再迁一次**（先 14→13
再 13→14，绕回原地）。

完整备选分析与迁移草图见 [历史版本/镜像基线-13.0备选.md](历史版本/镜像基线-13.0备选.md)。

## 后果

- 长期自担一个"从 CE 源码重构 14.0"的构建。可控：已跑通，且十二次失败已沉淀进
  `preflight-checks.py` 与 `verify-local.sh`。
- 触发本讨论的许可顾虑（不依赖 Pro 镜像）**在 14 上本就满足**——它从 CE 源码构建，
  不碰 Pro 镜像。
- 尾部风险：上游若永不发布 CE 14.0，就一直背这个重构。可控，且退回 13.0 也省不掉
  将来的迁移。

## 重启条件

仅当出现 14.0 特定反向驱动（上游明确不会发 CE 14.0、或 14.0 master 漂移到难以跟随、
或客户要 13.0-only）时，才重新考虑 13.0。
