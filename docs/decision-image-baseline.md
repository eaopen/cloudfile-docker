# 决策：镜像基线维持 CE 14.0（曾考虑退回 13.0，已否决）

一份架构决策记录（ADR）。配套：[BRANCHES.md](BRANCHES.md)（原则 0）、
[AGENTS.md](../AGENTS.md)（构建前提）、[storage.md](storage.md)。

## 决策（现行）

**维持现状：镜像基线保持"14.0 从 CE 源码构建"。** 曾提出退回 CE 13.0，评估后
**否决**——理由见下。当上游发布 CE 14.0 镜像/tag 时，改为基于该官方镜像（同版本
平移，几乎零成本）。

## 决策经过：为什么考虑 13.0，又为什么否决

### 一度倾向退回 13.0

原选择是 14.0，但"为什么 14.0 而非 13.0"从未记录。核对后，13.0 有几处明显优势
（均已验代码）：

| 事实 | 核对结果 |
|---|---|
| CE 14.0 是否发布 | ❌ 上游只有 `-pro` tag，无 CE 14.0 发布/镜像；14.0 CE 是从 master SHA 拼出来的 |
| CE 13.0 是否发布 | ✅ 已发布、有 `seafileltd/seafile-mc:13.0` 镜像、有 tag |
| 13.0 是否已含 roadmap 栈 | ✅ `repo_metadata`/`tags`/`file_tags`/`repo_tags`/`frontend/src/metadata`/seasearch 全在，Django 同为 5.2 |
| 扩展点目标 | ✅ 5 个补丁目标 + `check_folder_permission` + 身份映射 13.0 全有；`seahub-13`/`seafile-13` 为干净基座 |
| 14.0 相对 13.0 | 领先 1269 commit，但无新增子系统 |

按[原则 0（优先复用官方组件）](BRANCHES.md#〇首要原则优先复用官方组件)，
"用已发布、有官方镜像的 13.0"一度看起来是更一致的选择。

### 否决它的那个事实：13.0 也要重新编译

**CloudFile 修改了 C/Go 服务端**（`cf-ext.c` 的 ACL 强制与目录列举过滤，及将来的
S3 驱动），所以 `seaf-server`/`fileserver` 二进制**无论 13 还是 14 都得从 fork 编译**——
官方镜像里预编译的那份用不了。而 `seafile-mc` 本身也只是 `FROM ubuntu` + 复制发布包，
不是不可拆解的特殊基座。

**一旦"重新编译"两版都逃不掉，13.0 最大的卖点（复用官方镜像、免于从源码构建）
就基本蒸发了。** 决策于是退化为"更旧但已发布(13) vs 当前且已跑通(14)"，而多数
权衡都偏向 14：

| 维度 | 13.0 | 14.0（现行） |
|---|---|---|
| 服务端要不要重编 | 要 | 要 |
| 构建是否已跑通（12/12 冒烟） | ❌ 需重新建立 | ✅ 沉没成本已付 |
| 现在的迁移成本 | 5+8 个补丁按 13.0 行号重贴、dir-acl+SSO 重验 | **零** |
| 代码新旧 | 落后 1269 commit | 领先 |
| 上游发 CE 14.0 镜像后的前移 | **13→14 版本迁移（第二次迁移）** | 同版本换镜像，几乎免费 |

最后一行是关键：**先 14→13、将来再 13→14，是两次迁移，绕回原地。** 而留在 14，
将来是零或一次同版本换镜像。

### 13.0 残余的、但不足以翻盘的好处

1. **对着已发布/打 tag 的代码构建**——但 CloudFile 本就 pin SHA、按需 bump，可复现性已受控。
2. **上游跟随更平静**（13.x 维护线 vs 活跃 master）——真实，但在"pin 住、主动 bump"
   的模式下差距不大。
3. **产品口径**——13.0 是 CE 用户实际在跑的版本，"CloudFile 14.0"会引出"上游哪来
   的 CE 14.0"。营销层面的细节，非工程约束。

三者都不足以抵消"一次迁移 + 落后 1269 commit + 将来还要再迁一次"。

## 需要如实记下的一条

留在 14 意味着**长期自担一个"从 CE 源码重构 14.0"的构建**。但：

- 它**已经跑通**，十二次失败已付清并沉淀进 `preflight-checks.py` 与 `verify-local.sh`。
- 触发这次讨论的许可顾虑（不依赖 Pro 镜像）**在 14 上本就满足**——它从 CE 源码构建，
  不碰 Pro 镜像。
- 唯一的尾部风险是"上游若永不发布 CE 14.0，就得一直背这个重构"。可控，且退回 13.0
  也省不掉将来的迁移。

## 退出路径

**当上游发布 CE 14.0 镜像/tag** —— 基线平移到该官方镜像（甚至直接 `FROM` 它叠加
自编译的服务端二进制），"从源码重构 CE"这条路即可退休。因为已在 14.0，这是**同版本
平移**，不是版本迁移。

## 若将来重新考虑 13.0（迁移概要，备查）

仅当出现 14.0 特定的反向驱动（如上游明确不会发 CE 14.0、或 14.0 master 漂移到难以
跟随）时才重启：从 `origin/seahub-13`/`origin/seafile-13` 干净基座重接
`cloudfile_ext` + `cf-ext.c` + 补丁（按 13.0 行号）；`release.yaml` 重 pin 到 13.0 SHA；
Dockerfile 以仓库已有的 `image/seafile_13.0/Dockerfile` 为起点；重跑基线 + dir-acl +
SSO 门禁。

## 结论一句话

重新编译两版都免不了，于是 13.0"复用官方镜像"的核心收益不成立；14 已跑通、更新、
迁移成本为零，且前移路径更短。**维持 14，等官方 CE 14.0 镜像出来再平移。**
