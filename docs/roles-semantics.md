# CloudFile 五级角色规格与决策

> **用途**：回答「查看者/下载者/编辑者/内容管理员/空间管理员」五级角色在 CloudFile 里是
> 落地还是沿用 CE 现有 perm，并把结论固化成下游 P2-03 权限裁剪、P2-06 权限变化提示、
> P2-07 标签权限共同遵守的口径。
> **适用版本**：CloudFile `dev`，基于 Seafile CE 14 源码重构。
> **状态**：当前有效决策；评审清单 `couldfile_review20260814.md` 的「五级角色」项按本文件标注「不采纳」。
> **边界**：本文件只决定权限**口径**，不新增任何权限位、表结构或求解逻辑；目录级终判
> 仍以 [acl-semantics.md](acl-semantics.md) 为准。

---

## 0. 决策摘要

**沿用 CE 现有 perm（`r` / `rw` / `admin`），不落地五级角色抽象。**

- 评审清单建议的五级角色（查看者/下载者/编辑者/内容管理员/空间管理员）标注**「不采纳」**，
  并据此**删除** P2-02 用例集中依赖角色粒度的用例。
- 本文件 §3 保留「角色 → CE perm 换算」与 §4 继承规则，仅作**信息性说明**，供前端按
  CE 权限位渲染按钮时参考，不构成新的权限模型，不进入权限终判热路径。

---

## 1. 为什么先做这个决策

P2-03（搜索结果权限裁剪）、P2-06（移动前权限影响提示）、P2-07（标签权限）都要回答同一个
问题：**"某用户对某对象能做什么"以什么为口径？** 如果三处各自发明一套"角色"，就会在同一
权限语义上出现第二、第三份实现——而 AGENTS.md 的铁律是跨层语义只有一份真源，漂移在权限
系统里意味着安全漏洞。

所以先把口径定死：**权限终判只有 CE perm 一份**，角色只是 UI 层的展示映射（可选），
不进入求解。

---

## 2. CE 现有权限模型（唯一真源）

Seahub 的仓库/文件夹权限常量（`seahub/constants.py`）：

| 常量 | 值 | 含义 | CE 是否可用 |
|---|---|---|---|
| `PERMISSION_READ` | `r` | 读：浏览、搜索、下载 | 是 |
| `PERMISSION_READ_WRITE` | `rw` | 读写：读 + 上传/新建/编辑/重命名/移动/删除 | 是 |
| `PERMISSION_ADMIN` | `admin` | 库所有者/管理员：管理成员与权限 | 是 |
| `PERMISSION_PREVIEW` | `preview` | 仅网页预览，不可下载 | 否（Pro） |
| `PERMISSION_PREVIEW_EDIT` | `cloud-edit` | 仅网页预览+编辑，不可下载 | 否（Pro） |
| `PERMISSION_INVISIBLE` | `invisible` | 目录列举时整条剔除 | CloudFile dir_acl 扩展 |
| `CUSTOM_PERMISSION_PREFIX` | `custom*` | 自定义权限 | 否（Pro） |

两条硬约束，见 [acl-semantics.md](acl-semantics.md)：

1. **CE 的库级权限是上限**；CloudFile 目录 ACL 只能**收紧**，绝不能放宽。
2. dir_acl 的取值构成全序链 `invisible < none < r < rw`，`preview`/`cloud-edit`/`custom-*`
   不在这条链上，只能被 `invisible`/`none` 一票否决，其余情况原样保留。

结论：**CE 里真正可用的自主权限只有三级——`r`、`rw`、`admin`**，外加目录级的
`none`/`invisible` 收紧。没有"能看不能下载"、也没有"能编辑不能移动"这两个中间态。

## 3. 五级角色 → CE perm 换算（信息性，不落地）

评审建议的五级角色与 CE perm 的对应如下。**这份映射只说明"如果要在 UI 上展示角色，每个
角色等价于哪个 CE 权限"；它不新增任何角色枚举、不新增权限位。**

| 评审角色 | 对应 CE perm | 说明 |
|---|---|---|
| 查看者 | `r`（理想是 `preview`） | 浏览/搜索在 CE 即 `r`；"不可下载"需要 Pro 的 `preview` 位，CE 没有 |
| 下载者 | `r` | CE 的 `r` 天然含下载，无法与"查看者"区分 |
| 编辑者 | `rw` | 新建/编辑即 `rw`；"不可移动/删除"需要更细的写位，CE 没有 |
| 内容管理员 | `rw` | `rw` 天然含移动/删除，无法与"编辑者"区分 |
| 空间管理员 | `admin` | 库所有者/管理员 |

五级折叠为三级：

```
查看者 = 下载者 = r        编辑者 = 内容管理员 = rw        空间管理员 = admin
```

评审表里带"受策略控制"的格子（查看者的下载/复制、编辑者的移动/删除、内容管理员的修改
权限）在 CE 里没有对应的权限位去表达，落地它们就需要**新增写细分位或策略引擎**——那正是
"平行权限模型"，予以否决（见 §5）。

---

## 4. 继承规则

沿用 CE 与 CloudFile dir_acl 的既有规则，**角色不额外引入继承层**：

1. **库级**：repo 共享权限（`r`/`rw`/`admin`）作用于整个库，是上限。
2. **目录级**：dir_acl 规则从根向下逐层求解，深层的命中规则覆盖浅层；中间层无命中规则时
   继承最近的祖先决定（见 acl-semantics.md §4）。
3. **收紧不变量**：最终权限 ⊆ 原生权限；扩展只能收紧。

由于五级角色不落地，**"角色继承"不构成任何新语义**——前端若要做角色化展示，直接读
`resolve()` 的结果（`r`/`rw`/`admin`/`none`/`invisible`）再套 §3 的换算表即可，不改终判。

---

## 5. 决策理由：为什么不落地

1. **复用 CE 是铁律。** AGENTS.md：默认复用 Seafile CE，不为接入组件新建专用协议或平行
   后端。五级角色的粒度（查看者 vs 下载者、编辑者 vs 内容管理员）在 CE 里**没有权限位**
   支撑，落地 = 新增权限位或策略引擎 = 平行权限模型。
2. **漂移风险。** 权限语义在 Hub（Python）与 Server（C）两端各有一份实现，加一层"角色
   求解"就要在两端再各写一份角色→位映射，任何一处不一致都是安全漏洞。少一份实现 =
   少一处漂移。
3. **安全不变量只支持收紧。** 角色层的"下载/复制受策略控制""移动/删除受策略控制"本质是
   放宽或再收紧 CE 的 `r`/`rw`，这要求新的判定逻辑，且无法用 `min(native, decision)`
   表达，强行排序会在某个方向放宽权限。
4. **成本收益不对称。** CE 的 `r`/`rw`/`admin` 已覆盖评审里**可表达**的大部分能力；不可
   表达的部分（不可下载、编辑不可移动）不是当前 CloudFile 的交付范围，为它引入新权限位
   不值。

---

## 6. 对下游 P2-03 / P2-06 / P2-07 的口径

- **P2-03 权限裁剪**：搜索/自动补全/数量统计只按 `resolve(user, repo, path)` 的终判结果
  过滤，返回值只有 CE perm（`r`/`rw`/`admin`/`none`/`invisible`），**不产生角色名**。
- **P2-06 权限变化提示**：移动前后分别对源、目标计算"哪些主体还能读/写"，用 CE perm 差
  值表达（例如"N 名成员由 `rw` 降为不可访问"），**不引用角色名**。
- **P2-07 标签权限**：系统标签只读/用户标签可编辑的判定用 CE 权限位——系统标签变更仅
  `admin` 可用，用户标签编辑需 `rw` 及以上；**不引入"内容管理员/空间管理员"角色**。
