# 修订史与教训

正式文档只写最终结论。这里记它们**怎么演化到最终结论**，以及两处被更正的判断——
因为这些推理能防止同样的错误再犯。

---

## 一、探针 1（元数据）：结论演化了三版

最终结论（见 [../upstream-reuse.md](../upstream-reuse.md) 探针 1）：**默认用官方
`seafile-md-server`，自建协议兼容后端作后备。** 它经历了三版：

| 版本 | 结论 | 视角 |
|---|---|---|
| 第一版 | 别重写前端，写个协议兼容的服务 | 成本 |
| 第二版 | 为了整套开源/可分发，把权威模型收回自己手里，自建存储引擎 | 归属 |
| 第三版（最终） | 优先复用官方镜像（原则 0），自建降级为后备 | 复用官方优先 |

三版不矛盾，是同一件事在不同优先级下的排序。**承重的事实始终没变**：唯一闭源的
是协议背后的存储引擎，前端/API/投喂管线全开源——所以 `METADATA_SERVER_URL` 指向
谁都行，官方与自建可随时互换。第三版之所以成为最终版，是因为确立了[原则 0
（优先复用官方组件）](../BRANCHES.md)，把"起点用官方、自建作后备"定了下来。

## 二、被更正的判断之一：seasearch"零 CloudFile 代码"

**错误表述**：探针 3 一度写"seasearch 端到端零 CloudFile 代码"。

**为什么错**：全局搜索接口 `seahub/api2/views.py:458 class Search` 被
`permission_classes = (IsAuthenticated, IsProVersion)` 挡着，CE 下恒 403——即便
seasearch 配好也搜不了。

**最终表述**（见 [../search.md](../search.md)）：seasearch 的**索引与查询后端**零
新增代码（都在 seafevents），但**接口那层 Pro 门必须由 CloudFile 解除**（只影响
`Search` 与 `public_repos_search` 两个接口，经 URL 影子子类覆盖 `permission_classes`，
零上游改动；**不要动全局 `is_pro_version()`**——它被 56 个文件引用）。零的是后端，
不是端到端。

## 三、被更正的判断之二：S3"1 个新增登记项"

**错误表述**：EXTENSION-POINTS 缺口 4 与 BRANCHES"反直觉结论"一度写 S3"比预想便宜，
代价收敛到一个 `obj-store.c` 后端选择改动"，依据是"seafobj 上游已带 S3"。

**为什么错**：seafobj 只是 **Python 读侧**（seahub 缩略图、seafevents 索引读对象），
**不在核心写入/服务路径上**。核心路径是 Go fileserver（`fileserver/objstore/` 只有
`backend_fs.go`）与 C seaf-server/GC/FSCK（`obj-store.c` 只有 fs + 遗留 riak）——
**两处都只有 FS 后端**。

**最终表述**（见 [../storage.md](../storage.md)）：S3 要在 Go 和 C 两侧各补一个存储
驱动 + 多存储路由，覆盖服务/GC/FSCK/迁移，是 roadmap 里**最重**的构建项之一，不是
最轻。

## 四、通用教训

这三处（含探针 1 的反复）指向同几条：

1. **只看一层会漏掉承担写入的那一层。** S3 看了 seafobj（读侧）漏了 Go/C（写侧）；
   审计看了钩子注册漏了"没有触发点"。**问"谁真正把字节写下去/把回调触发"，
   而不是"谁看起来实现了"。**
2. **一份对"闭源/开源边界"含糊的探针，正是日后误导实现者的东西。** 所以探针要把
   边界钉到文件级（元数据的闭源边界只有存储引擎；seasearch 的门只有两个接口）。
3. **记下反转，别静默翻页。** 一个被否决的备选如果不留档，就会被重新提出；一个
   被更正的判断如果直接改掉，读者无从知道新结论比旧的更可信。所以正式文档写最终
   结论 + 一行指向这里，这里写"曾经错在哪、为什么改"。
4. **先查上游再动工。** 每个探针都是这条的实证：花十分钟到两天读代码，换来砍掉
   数千行本要自己维护的重写（认证后端、属性/标签前端、自研检索）。
