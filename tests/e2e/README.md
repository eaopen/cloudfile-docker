# End-to-end 测试分层

两类问题必须分开问，否则默认门禁会被拖到一小时以上：

| 层 | 位置 | 何时跑 | 回答的问题 |
|---|---|---|---|
| 冒烟（默认） | `smoke.py` | 每次改动后 | 服务起得来吗？登录、上传、下载、目录列表这些主路径还通吗？ |
| 全量矩阵（参考） | `full/` | 专项验收、回归排查 | 开着某个开关时，每个入口是否真的执行了那条规则？ |

## 冒烟

```bash
./tools/gates/verify-local.sh e2e        # 假设镜像已构建（先跑 build）
```

`smoke.py` 只依赖栈是默认态，不重启容器，几分钟内出结论。

## 全量矩阵

```bash
./tools/gates/verify-local.sh e2e-full   # 很慢：每个能力都要带开关重启一次栈
./tools/gates/verify-local.sh cap acl    # 只跑一个能力
```

`full/` 里的能力脚本由 `verify-local.sh` 的 `CAPABILITIES` 登记项（开关组合 +
脚本路径）驱动；需要额外配置、跑多遍或追加浏览器断言的用 `cap_<名>_env` /
`cap_<名>_run` 钩子表达（`review_ui_*.py` 就是挂在对应能力钩子后面的浏览器套件，
不在表里单列）。它们不是默认门禁：一轮下来接近一小时，而且要求本机 80/443 空闲。
`ai_matrix.py` 目前不登记——CE 不发布 seafile-ai 镜像，开 `CF_AI_ENABLED` 会让
原生冒烟先坏，属已知运行级技术负债。

`full/` 同时保留 `baseline.py`（扩展点装载基线）与三份 `EDITING_*.md`
（本地编辑验收记录），都属"参考与追溯"，不是每次改动都要过的关口。

全量矩阵失败时**不要**用它替代冒烟结论：先看冒烟是否通过，冒烟挂了说明是启动
或主路径问题，矩阵的报错只是下游症状。

这份说明只管 E2E 这一层。根级契约测试、Shell 契约测试、跨仓用例集与夹具的
位置和跑法见 [tests/README.md](../README.md)。
